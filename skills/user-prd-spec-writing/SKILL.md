# Product Requirements Specification

## Purpose and scope

Separate the user problem and outcome from the proposed solution, then define what must be true for the smallest useful release.

## Workflow

State context, users, problem, goals, non-goals, requirements, acceptance criteria, states and edge cases, dependencies, privacy/accessibility/security constraints, analytics, rollout, risks, and open questions; label assumptions and unresolved decisions.

## Verification and quality checks

Trace each requirement to an outcome or constraint, test acceptance criteria for observability, inspect contradictory requirements, verify feasibility with engineering and design, and identify what is deliberately excluded.

## Common errors

Common errors include writing solution detail before validating the problem, vague verbs, missing failure states, unowned dependencies, unmeasurable acceptance criteria, and scope creep hidden as a must-have.

## Rules, safety, and non-goals

Do not fabricate user research or promise technical, legal, financial, or compliance outcomes without evidence and responsible review. Do not invent sources, data, results, approvals, or completed actions. Preserve privacy and use the smallest relevant skill composition.

## Handoff

Return a versioned PRD with decision owner, requirements, acceptance criteria, non-goals, dependencies, risks, rollout, metrics, and review questions.
